# 산출물 보관(Archive) 기능

## Context

Sofia 2에는 결과물을 만들어내는 기능이 5개 있다 — PDF 내보내기, 이미지 병합(Merge), 콜라주(Collage), 이미지 효과(Effect), 슬라이드쇼(Slideshow). 지금은 다섯 개 모두 "생성 → 즉시 다운로드(또는 미리보기 후 다운로드)"로 끝나고, 결과물이 서버에 남지 않거나(PDF/Merge는 스트리밍 직후 임시파일 삭제) 남더라도(Slideshow는 정리 로직이 없어 계속 쌓임) 관리할 방법이 없다. 이번 작업은 이 5가지 산출물을 **DB 테이블 기반의 "보관소"에 저장하고, 메모(note)와 파일명을 나중에 편집할 수 있게** 만드는 것이다.

또한 UI 흐름을 모든 기능에서 동일하게 **"생성" → "출력물 처리"의 2단계**로 통일하고, 출력물 처리 단계에서 **다운로드 / 보관소에 저장 / 보관소에 저장 후 다운로드**(+ Merge에 한해 클립보드 복사)를 선택할 수 있게 하며, 5개 기능 모두에서 **생성에 걸린 시간**을 표시한다.

이 앱은 이미 jskn 서버에 배포되어 있으므로(Docker Tomcat, Postgres, Flyway/Liquibase 없이 `ddl-auto=update`만 사용), 배포 시 수동 DB 마이그레이션이나 서버 접속 없이 `./deploy.sh` 한 번으로 반영되도록 설계한다.

**이 문서는 계획서다 — 실제 구현은 이 문서 승인 후 별도로 진행한다.**

## 현재 상태 조사 요약

| 기능 | 생성 위치 | 현재 출력 방식 | 미리보기/2단계 존재? |
|---|---|---|---|
| **PDF** | 서버 (`ImageController.exportToPdf` → `ImageService.exportAsPdf`, PDFBox) | axios blob → 즉시 `<a download>` | ❌ 없음 (즉시 다운로드) |
| **Merge** | 서버 (`ImageController.exportToMergedImage` → `ImageService.exportAsMergedImage`) | axios blob → `MergePreviewModal`에서 다운로드/클립보드 복사 | ✅ 있음 (모델로 삼을 패턴) |
| **Collage** | **클라이언트 전용** (`collageRenderer.ts`, 백엔드 엔드포인트 자체가 없음) | canvas `toDataURL` → 즉시 `<a download>` | ❌ 없음 (모달 자체가 상시 미리보기) |
| **Effect** | **클라이언트 전용** (`imageEffectProcessors.ts`, 18개 픽셀 필터) | canvas `toDataURL` → 즉시 다운로드 (배치는 N개 개별 다운로드, zip 없음) | ❌ 없음 |
| **Slideshow** | 서버 (FFmpeg, `SlideShowService`) | 완료 후 `<video>` + MP4 다운로드 링크 | ✅ 있음 (완성 화면 단계, 여기에 버튼만 추가) |

**중요 사실:**
- PDF/Merge는 서버 임시파일을 스트리밍 직후 `Files.deleteIfExists`로 즉시 삭제한다 (temp file 재사용 불가 — 저장하려면 클라이언트가 이미 받은 blob을 다시 업로드해야 함).
- Slideshow는 반대로 임시 mp4를 스트리밍 후에도 삭제하지 **않고** 계속 남긴다 (`@Scheduled` 정리 작업이 프로젝트 전체에 전혀 없음 — 기존에 존재하던 문제이며 이번 작업 범위 밖이지만, 새 보관소도 같은 실수를 반복하지 않도록 유의).
- Slideshow의 "현재 폴더에 저장" 기능(`saveToFolder`)은 최근 커밋(`feeb3da`)에서 이미 제거됐다 — 이번 보관소 기능이 그 자리를 대체하는 개념이며, 제거된 코드(`Files.copy`로 소스 이미지 폴더에 복사)의 메커니즘을 보관소 폴더로 옮겨 재사용한다.
- `BgmAssetService`(BGM 라이브러리)는 DB 테이블 없이 파일시스템+파일명 키만으로 관리되는 반면, 이번 기능은 사용자가 명시적으로 "note를 적을 수 있는 table"을 요구했으므로 새 JPA 엔티티가 필요하다 — BGM과는 다른, 한 단계 더 나아간 설계.
- 프로젝트 전체에 Flyway/Liquibase가 없고 `spring.jpa.hibernate.ddl-auto=update`만 사용 — 새 엔티티는 다음 배포 시 자동으로 테이블이 생성된다.
- `application-jskn.properties`는 `deploy.sh`가 WAR를 빌드할 때 그대로 포함되므로, 서버에 별도로 접속해 파일을 고칠 필요가 없다 (`./deploy.sh` 한 번으로 끝).

## 속성명 결정 (요청 8번 답변)

`sofia.base.folder.repository=${sofia.base.folder}/repository`는 기존 컨벤션과 어긋난다. 기존 것들은 전부 `sofia.base.<카테고리>.folder`처럼 **`folder`가 맨 뒤**에 온다 (`sofia.base.image.folder`, `sofia.base.assets.bgm.folder`). 새로 추가한 것만 `folder`가 중간에, `repository`가 맨 뒤에 와서 패턴이 반대다.

또한 이 기능은 Spring Data의 `Repository`/`JpaRepository`와 헷갈리지 않도록 코드 전체에서 "Archive"라는 용어로 통일하기로 했으므로(엔티티 `ArchivedOutput`, `/api/archive`, 프론트 `/archive`), 속성명과 저장 폴더명도 "repository"가 아니라 **`sofia.base.archive.folder`**, 폴더는 `${sofia.base.folder}/archive`로 맞추는 것이 전체적으로 통일성 있다 (사용자 제안, 반영함).

**→ `sofia.base.archive.folder`로 이름을 바꾸고, base `application.properties`에도 기본값을 추가한다** (다른 두 개도 base 파일에 기본값이 있고 프로필 파일에서 실제 경로로 덮어쓰는 구조이므로 동일하게 맞춘다). **이미 반영 완료.**

3개 파일 수정 (완료):
```properties
# application.properties (base) — 새로 추가
sofia.base.archive.folder=${sofia.base.folder}/archive

# application-local.properties — 이름 변경 + 폴더명도 archive로 통일
sofia.base.archive.folder=${sofia.base.folder}/archive   # (기존: sofia.base.folder.repository=${sofia.base.folder}/repository)

# application-jskn.properties — 이름 변경 + 폴더명도 archive로 통일
sofia.base.archive.folder=${sofia.base.folder}/archive   # (기존: sofia.base.folder.repository=${sofia.base.folder}/repository)
```
새 서비스는 `@Value("${sofia.base.archive.folder:${sofia.base.folder}/archive}")`로 바인딩 (기존 `SlideShowService`의 `sofia.base.image.folder` 바인딩과 동일한 스타일).

## 백엔드 설계

용어 충돌 방지를 위해 "Repository"라는 이름 대신 **"Archive"**를 쓴다 (Spring Data의 `JpaRepository`/`@Repository`와 헷갈리지 않게).

### 1. 엔티티 — `backend/src/main/java/kr/co/kalpa/sofia/domain/ArchivedOutput.java`

기존 `ImageFolder.java`(domain 패키지 엔티티) 스타일 그대로 `@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder` 사용:

```java
@Entity
@Table(name = "archived_outputs")
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class ArchivedOutput {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private OutputType type; // PDF, MERGE, COLLAGE, EFFECT, SLIDESHOW

    @Column(nullable = false, unique = true)
    private String storedFilename; // 디스크상 실제 파일명, UUID 기반 (충돌 방지)

    @Column(nullable = false)
    private String displayFilename; // 사용자가 목록에서 편집 가능한 이름

    @Column(columnDefinition = "text")
    private String note; // 사용자 편집 가능한 메모

    private Long sourceFolderId; // 원본 폴더 스냅샷 (FK 아님, 추적용)

    @Column(nullable = false)
    private Long fileSize;

    @Column(nullable = false, length = 10)
    private String fileExtension; // "pdf","jpg","mp4" (점 없이)

    private Integer elapsedMs; // 생성에 걸린 시간(ms), nullable

    @Column(nullable = false)
    private LocalDateTime createdAt;

    @PrePersist
    void prePersist() {
        if (createdAt == null) createdAt = LocalDateTime.now();
    }
}
```

`OutputType`은 별도 파일 `domain/OutputType.java`:
```java
public enum OutputType { PDF, MERGE, COLLAGE, EFFECT, SLIDESHOW }
```
`@Enumerated(EnumType.STRING)`을 쓰는 이유: 타입 안정성 + `GET /api/archive?type=PDF` 같은 필터 쿼리 파라미터가 자동으로 바인딩/검증됨 (잘못된 값이면 자동 400).

### 3. 서비스 — `backend/src/main/java/kr/co/kalpa/sofia/service/ArchivedOutputService.java`

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class ArchivedOutputService {

    private final ArchivedOutputRepository archivedOutputRepository;
    private final SlideShowService slideShowService; // 기존 public 메서드 재사용, 슬라이드쇼 쪽 수정 불필요

    @Value("${sofia.base.archive.folder:${sofia.base.folder}/archive}")
    private String archiveFolderPath;

    private Path archiveDir;

    @PostConstruct
    public void init() {
        archiveDir = Paths.get(archiveFolderPath);
        if (!Files.exists(archiveDir)) {
            Files.createDirectories(archiveDir);
        }
    }

    // PDF/Merge/Collage/Effect 공통: 클라이언트가 이미 들고 있는 blob을 업로드
    public ArchivedOutput saveUpload(MultipartFile file, OutputType type, String displayFilename,
                                      String note, Long sourceFolderId, Integer elapsedMs) throws IOException {
        String extension = resolveExtension(type);
        String storedFilename = UUID.randomUUID() + "." + extension;
        Path target = archiveDir.resolve(storedFilename);
        Files.copy(file.getInputStream(), target, StandardCopyOption.REPLACE_EXISTING);

        String finalName = normalizeDisplayFilename(
                StringUtils.hasText(displayFilename) ? displayFilename : file.getOriginalFilename(), extension);

        return archivedOutputRepository.save(ArchivedOutput.builder()
                .type(type).storedFilename(storedFilename).displayFilename(finalName)
                .note(note).sourceFolderId(sourceFolderId)
                .fileSize(Files.size(target)).fileExtension(extension).elapsedMs(elapsedMs)
                .build());
    }

    // Slideshow 전용: 서버에 이미 있는 임시 mp4를 브라우저 왕복 없이 그대로 복사
    public ArchivedOutput saveFromSlideshowTask(String taskId, String displayFilename,
                                                 String note, Integer elapsedMs) throws IOException {
        Path source = slideShowService.getVideoPath(taskId); // 이미 존재하는 public 메서드
        if (source == null) throw new IllegalStateException("완료된 슬라이드 쇼 동영상을 찾을 수 없습니다.");

        String storedFilename = UUID.randomUUID() + ".mp4";
        Path target = archiveDir.resolve(storedFilename);
        Files.copy(source, target, StandardCopyOption.REPLACE_EXISTING);

        String finalName = normalizeDisplayFilename(
                StringUtils.hasText(displayFilename) ? displayFilename : "slideshow", "mp4");
        var status = slideShowService.getTaskStatus(taskId); // 이미 존재하는 public 메서드

        return archivedOutputRepository.save(ArchivedOutput.builder()
                .type(OutputType.SLIDESHOW).storedFilename(storedFilename).displayFilename(finalName)
                .note(note).sourceFolderId(status != null ? status.getFolderId() : null)
                .fileSize(Files.size(target)).fileExtension("mp4").elapsedMs(elapsedMs)
                .build());
    }

    public List<ArchivedOutput> list(OutputType typeFilter) {
        return typeFilter != null
                ? archivedOutputRepository.findByTypeOrderByCreatedAtDesc(typeFilter)
                : archivedOutputRepository.findAllByOrderByCreatedAtDesc();
    }

    public ArchivedOutput updateMeta(Long id, String note, String displayFilename) {
        ArchivedOutput item = getMeta(id);
        if (note != null) item.setNote(note);
        if (StringUtils.hasText(displayFilename)) {
            item.setDisplayFilename(normalizeDisplayFilename(displayFilename, item.getFileExtension()));
        }
        return archivedOutputRepository.save(item);
    }

    public void delete(Long id) {
        ArchivedOutput item = getMeta(id);
        try { Files.deleteIfExists(archiveDir.resolve(item.getStoredFilename())); }
        catch (IOException e) { log.warn("보관 파일 삭제 실패: {}", item.getStoredFilename(), e); }
        archivedOutputRepository.delete(item);
    }

    public Resource getFileForDownload(Long id) {
        Path path = archiveDir.resolve(getMeta(id).getStoredFilename());
        return Files.exists(path) ? new FileSystemResource(path) : null;
    }

    public ArchivedOutput getMeta(Long id) {
        return archivedOutputRepository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("항목을 찾을 수 없습니다: " + id));
    }

    private String resolveExtension(OutputType type) {
        return switch (type) {
            case PDF -> "pdf";
            case MERGE, COLLAGE, EFFECT -> "jpg";
            case SLIDESHOW -> "mp4";
        };
    }

    // 확장자를 강제로 type에 맞게 교정 (제거된 saveToFolder의 ".mp4" 강제 로직을 일반화)
    private String normalizeDisplayFilename(String raw, String extension) {
        String base = raw.replaceAll("[\\\\/:*?\"<>|]", "_").trim();
        int dot = base.lastIndexOf('.');
        if (dot > 0) base = base.substring(0, dot);
        return base + "." + extension;
    }
}
```

**슬라이드쇼 쪽은 코드 수정이 전혀 필요 없다** — `SlideShowService.getVideoPath(String)`(완료 상태+파일 존재 확인 후 `Path` 반환)와 `getTaskStatus(String)`가 이미 public으로 존재해서 그대로 재사용 가능함을 코드로 직접 확인했다.

**왜 저장 경로가 2가지(멀티파트 업로드 vs 서버 내부 복사)인가**: PDF/Merge/Collage/Effect는 "출력물 처리" 단계에 도달한 시점에 브라우저가 이미 결과 바이트를 blob으로 들고 있다(서버는 스트리밍 직후 자기 임시파일을 지워버림, Collage/Effect는 애초에 서버에 간 적이 없음) — 그래서 업로드해야 한다. Slideshow는 반대로 서버 디스크에 완성된 mp4가 이미 남아있으므로, 굳이 브라우저로 큰 동영상 파일을 왕복시키지 않고 서버 내부 `Files.copy`로 처리한다.

### 4. 컨트롤러 — `backend/src/main/java/kr/co/kalpa/sofia/controller/ArchivedOutputController.java`

```java
@RestController
@RequestMapping("/api/archive")
@RequiredArgsConstructor
public class ArchivedOutputController {

    private final ArchivedOutputService archivedOutputService;

    @PostMapping("/upload")
    public ResponseEntity<ArchivedOutput> upload(
            @RequestParam("file") MultipartFile file,
            @RequestParam("type") OutputType type,
            @RequestParam(required = false) String displayFilename,
            @RequestParam(required = false) String note,
            @RequestParam(required = false) Long sourceFolderId,
            @RequestParam(required = false) Integer elapsedMs) throws IOException {
        return ResponseEntity.ok(archivedOutputService.saveUpload(
                file, type, displayFilename, note, sourceFolderId, elapsedMs));
    }

    @PostMapping("/from-slideshow/{taskId}")
    public ResponseEntity<ArchivedOutput> fromSlideshow(
            @PathVariable String taskId, @RequestBody SlideshowArchiveRequest request) throws IOException {
        return ResponseEntity.ok(archivedOutputService.saveFromSlideshowTask(
                taskId, request.getDisplayFilename(), request.getNote(), request.getElapsedMs()));
    }

    @GetMapping
    public ResponseEntity<List<ArchivedOutput>> list(@RequestParam(required = false) OutputType type) {
        return ResponseEntity.ok(archivedOutputService.list(type));
    }

    @PatchMapping("/{id}")
    public ResponseEntity<ArchivedOutput> updateMeta(@PathVariable Long id,
            @RequestBody ArchivedOutputUpdateRequest request) {
        return ResponseEntity.ok(archivedOutputService.updateMeta(id, request.getNote(), request.getDisplayFilename()));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        archivedOutputService.delete(id);
        return ResponseEntity.noContent().build();
    }

    @GetMapping("/{id}/download")
    public ResponseEntity<Resource> download(@PathVariable Long id) {
        ArchivedOutput meta = archivedOutputService.getMeta(id);
        Resource resource = archivedOutputService.getFileForDownload(id);
        if (resource == null) return ResponseEntity.notFound().build();
        ContentDisposition disposition = ContentDisposition.attachment()
                .filename(meta.getDisplayFilename(), StandardCharsets.UTF_8).build();
        return ResponseEntity.ok().header(HttpHeaders.CONTENT_DISPOSITION, disposition.toString()).body(resource);
    }
}
```

새 DTO 2개 (`backend/src/main/java/kr/co/kalpa/sofia/dto/`, 기존 `ImageExportRequest` 스타일 그대로 plain getter/setter):
- `SlideshowArchiveRequest { String displayFilename; String note; Integer elapsedMs; }`
- `ArchivedOutputUpdateRequest { String note; String displayFilename; }`

## 프론트엔드 설계

### 1. 공통 컴포넌트 — `frontend/src/shared/components/OutputActionsPanel.tsx`

5개 기능이 전부 이 패널을 쓴다. 새로 만드는 이유: 각 기능마다 아키텍처가 다 달라서(서버 렌더/클라이언트 렌더, 미리보기 있음/없음) 버튼 로직을 5번 중복시키지 않기 위함.

```tsx
export type ArchiveOutputType = 'PDF' | 'MERGE' | 'COLLAGE' | 'EFFECT' | 'SLIDESHOW';

interface OutputActionsPanelProps {
  elapsedMs: number | null;
  onDownload: () => void | Promise<void>;
  onSaveToArchive: (meta: { note?: string; displayFilename?: string }) => Promise<void>;
  onSaveThenDownload: (meta: { note?: string; displayFilename?: string }) => Promise<void>;
  onCopyToClipboard?: () => Promise<void>; // Merge에서만 전달
  defaultFilename: string;
  isSaving?: boolean;
  saved?: boolean;
  saveError?: string | null;
}
```
내부 구성: (1) 상단에 "생성 완료 (X.X초 소요)" 텍스트, (2) 접이식 파일명/메모 입력(기본값 채워짐), (3) 버튼 행 [다운로드] [보관소에 저장] [보관소에 저장 후 다운로드] (+ `onCopyToClipboard`가 있으면 [클립보드로 복사]). `shared/components/`에 두는 이유: `domain/folder/` 밖에서도 재사용 가능한 범용 UI라서 (다른 `shared/components/ui/*` 프리셋들과 같은 위치).

### 2. 경과시간 유틸 — `frontend/src/shared/utils/elapsedTime.ts`

```typescript
export const useElapsedTimer = () => {
  const startRef = useRef<number | null>(null);
  const start = () => { startRef.current = performance.now(); };
  const stop = (): number => startRef.current != null ? Math.round(performance.now() - startRef.current) : 0;
  return { start, stop };
};
export const formatElapsed = (ms: number) => `${(ms / 1000).toFixed(1)}초 소요`;
```
API 호출은 이 프로젝트 컨벤션대로 별도 헬퍼 함수 없이 `apiClient`를 각 컴포넌트에서 직접 호출 (`frontend/src/lib/api.ts`는 지금도 axios 인스턴스만 export하고, 도메인별 API 헬퍼 모듈이 따로 없는 게 기존 패턴 — 그대로 따른다).

### 3. 기능별 리팩토링

**PDF** — 지금 미리보기 단계가 아예 없다 (`handleExportPdf`가 바로 다운로드). `MergePreviewModal.tsx`와 거의 동일한 구조로 새 `PdfResultModal.tsx`를 만든다 (PDF는 `<img>`로 미리 볼 수 없으니 "PDF 생성 완료" 요약 + `OutputActionsPanel`만 표시, 클립보드 버튼 없음). `ImageListPage.tsx`의 `handleExportPdf`는 자동 다운로드를 멈추고 `pdfResultBlob`/`pdfResultFilename`/`pdfElapsedMs`를 상태로 저장 후 모달을 연다 (Merge와 완전히 같은 패턴).

**Merge** — `MergePreviewModal.tsx`를 그대로 확장. 기존 `handleCopy`(PNG 변환 + `ClipboardItem`)는 손대지 않고, 하단 버튼 영역에 `OutputActionsPanel`을 놓고 `onCopyToClipboard={handleCopy}`로 넘긴다. `ImageListPage.handleMergeImages`에 `useElapsedTimer`로 axios 호출 앞뒤를 감싸 `elapsedMs`를 구해 모달에 전달.

**Collage** — 별도 미리보기 단계가 필요 없다 (모달 자체가 상시 미리보기). `CollageModal.tsx`의 기존 다운로드 버튼 옆에 `OutputActionsPanel` 버튼들을 바로 추가. "보관소에 저장"은 기존과 동일하게 2400px 오프스크린 캔버스로 렌더링한 뒤 `canvas.toDataURL()` → `fetch(dataUrl).then(r => r.blob())`로 Blob 변환 → `type=COLLAGE`로 멀티파트 업로드. 경과시간은 렌더링 시작~완료 구간을 측정.

**Effect** — 싱글/배치를 구분해서 처리한다.
- 싱글(`handleDownloadSingle`): 기존 다운로드 버튼 옆에 `OutputActionsPanel` 추가, Collage와 동일한 canvas→blob→업로드, `type=EFFECT`, 1행 생성.
- 배치(`handleDownloadBatch`): 기존 `for` 루프 구조를 그대로 유지하면서 "일괄 보관소에 저장" 액션을 추가 — 이미지 개수만큼 개별 업로드하여 **N개의 개별 행**을 만든다 (지금도 zip 없이 N개 파일을 따로 다운로드하는 구조와 동일한 원칙). 경과시간은 배치 전체 소요시간 1개만 표시.

**Slideshow** — 완성 화면(`상태 2`)에 있는 기존 "MP4 다운로드" 링크 옆에 `OutputActionsPanel`(클립보드 버튼 없음)을 추가. `onSaveToArchive`는 `apiClient.post('/archive/from-slideshow/{taskId}', {displayFilename, note, elapsedMs})`처럼 순수 JSON POST (바이트 업로드 없음). **선행 수정 필요**: 현재 `const [, setTaskId] = useState<string | null>(null);`로 `taskId` 값 자체를 버리고 있어서(이전 "현재 폴더에 저장" 제거 때 같이 정리됨) `const [taskId, setTaskId] = ...`로 되돌려야 archive 호출에 taskId를 쓸 수 있다. 경과시간은 생성 요청 시작 ~ 폴링에서 `COMPLETED` 확인 시점까지로 측정.

## jskn 배포 시 고려사항

`deploy.sh`를 직접 확인한 결과: 프론트 빌드 → `dist/`를 `backend/src/main/resources/static/`으로 복사 → `gradlew war` → sftp로 WAR 전송, 이 4단계뿐이고 서버에 별도 외부 properties 파일이 없다 (`application-jskn.properties`가 WAR 안에 그대로 패키징됨). 따라서:

1. **서버 접속해서 파일 고칠 필요 없음** — 저장소의 `application-jskn.properties`를 고치고 `./deploy.sh`만 다시 돌리면 됨.
2. **수동 DB 마이그레이션 필요 없음** — `ddl-auto=update`가 새 `archived_outputs` 테이블을 앱 기동 시 자동 생성.
3. **수동 디렉토리 생성 필요 없음** — `ArchivedOutputService.init()`(`@PostConstruct`)이 `BgmAssetService`/`SlideShowService`와 동일한 방식으로 `${sofia.base.folder}/archive` 폴더를 없으면 자동 생성.
4. 배포 순서: WAR 교체 → Tomcat 재기동 → Hibernate DDL 업데이트(`archived_outputs` 테이블 생성) → `ArchivedOutputService.init()` 실행 → `/archive` 페이지와 `/api/archive/*` 정상 동작. 별도 다운타임 이슈 없음 (Tomcat이 WAR 교체 시 어차피 한 번 재기동).
5. 참고: jskn의 `/data/pictures/sofia/` 마운트에 Tomcat 실행 계정 쓰기 권한과 여유 공간이 있는지 정도만 배포 전에 확인하면 됨 (특히 슬라이드쇼는 `temp/`와 `archive/`에 동영상이 중복으로 쌓일 수 있음 — 아래 리스크 참고).

## 리스크 / 엣지케이스

1. **디스크 무한 증가**: 기존 슬라이드쇼 임시폴더처럼 정리 로직이 없으면 보관소도 계속 쌓인다. 이번 1차 범위에서는 예약 정리 작업(스케줄러)까지는 만들지 않고, `ArchiveListPage`에 체크박스 다중선택 + "선택 삭제" 버튼만 넣어 사용자가 수동으로 정리할 수 있게 한다. 자동 만료/정리 정책은 별도 후속 작업으로 남긴다 (슬라이드쇼 temp 폴더 정리 문제와 같은 급의 기존 이슈이며, 이번 기능이 새로 만드는 문제는 아님).
2. **파일명 충돌**: `storedFilename`은 `UUID + 확장자`라 사실상 충돌 불가능하고, DB에도 `unique` 제약을 걸어 이중으로 방지한다 (BGM 라이브러리처럼 `_1`, `_2` 붙이는 방식과 달리, 서로 다른 두 생성 작업이 절대 같은 파일을 덮어써선 안 되므로).
3. **확장자 교정**: `displayFilename`을 목록에서 자유롭게 고칠 수 있으므로, 저장/수정 시 서버 쪽에서 `type`에 맞는 확장자를 강제로 교정한다(`normalizeDisplayFilename`) — 제거된 `saveToFolder`가 `.mp4`를 강제로 붙이던 로직과 같은 원리를 5개 타입 전체로 일반화. 클라이언트 검증만으로는 부족하므로 반드시 서버에서도 처리.
4. **기존 다운로드 경로 회귀 없음**: PDF/Merge가 "저장 없이 그냥 다운로드"할 때는 기존 `FileSystemResource` 스트리밍-후-삭제 로직을 그대로 두고 건드리지 않는다. "보관소에 저장"은 클라이언트가 이미 받은 blob을 별도 업로드 요청으로 보내는 것이라 서버 임시파일 생명주기와는 무관하다 — 검증 단계에서 회귀 여부 확인 필요.
5. **Effect 배치 저장 → N개 행**: 지금도 zip 없이 N개 파일을 따로 다운로드하는 구조와 일관되게, 배치 저장도 N개의 독립된 `ArchivedOutput` 행을 만든다 (배치를 묶는 개념 없음).

## 검증 방법

1. `./bm.sh run` + `./fm.sh dev` 실행, 백엔드 로그(`show-sql=true`)에서 첫 기동 시 `archived_outputs` 테이블 생성 DDL이 찍히는지 확인.
2. **PDF**: 내보내기 → 새 결과 모달이 뜨는지(자동 다운로드 안 함) → 경과시간 표시 확인 → 다운로드 클릭(서버 temp 파일 정상 삭제 확인) → 다시 생성 후 "보관소에 저장" → `/archive`에서 PDF 행 확인, 파일명/메모 편집 후 새로고침해도 유지되는지 확인.
3. **Merge**: 기존 미리보기/클립보드 복사(다른 앱에 붙여넣기로 확인)가 그대로 되는지 → 보관소 저장/저장 후 다운로드 확인.
4. **Collage**: 두 새 버튼으로 저장 → 보관소에서 다운로드한 파일이 정상 이미지인지 확인.
5. **Effect**: 싱글 저장 시 1행, 3장 배치 저장 시 정확히 3행 생성되는지, 파일명이 기존 네이밍 규칙과 일치하는지 확인.
6. **Slideshow**: `taskId` 상태 복구가 "다시 설정하기" 흐름을 깨지 않는지 확인 → 보관소 저장 시 네트워크 탭에서 동영상 바이트가 아니라 작은 JSON만 전송되는지 확인 → 저장된 사본이 원본 태스크와 독립적으로(원본을 지워도) 재생되는지 확인.
7. `/archive` 페이지: 타입 필터, 정렬, 5종 각각 최소 1건씩 파일명/메모 인라인 편집 후 새로고침 유지 확인, 다운로드/삭제(DB 행+실제 파일 모두 삭제) 확인, 다중선택 후 "선택 삭제" 동작 확인.
8. 5개 기능 모두에서 "생성 완료 (X.X초 소요)" 텍스트가 실제로 보이는지 최종 확인.
